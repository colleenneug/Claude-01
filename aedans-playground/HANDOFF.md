file into a new session to resume. The long-term plan is `ROADMAP.md`; how
to build, run and troubleshoot is in `README.md`.

  engine architecture, memory management and data-oriented design, and to
  host **Erebus Cradle** (the OpenGL 4.1 game in `../cpp/`) once it is ready.

  branch `claude/relaxed-cray-5kc2fl` (38 commits, `d065ae6` → this one). No

## 1. Full Library Architecture

Each folder is a static library with its own public `include/`. A layer may
include only the layers below it, so a wrong `#include` is a build error.
Vulkan types never appear above `render`'s private sources; ENet never
appears outside `net/src/Host.cpp`; Jolt never appears outside
`physics/src/PhysicsWorld.cpp`; tinygltf and stb never appear outside
`engine/src/Gltf*.cpp` and `EnvironmentAsset.cpp`.

```
            app  (scenes, --server, --connect)
             │
            game (protocol, prediction, server, client)
           /   \
      engine    net ──────────┐
     /   |  \                 │
render physics ─ ecs          │
    │  (gpu private; Jolt private to physics)
   gpu                        │
    │                         │
 platform                     │
    │                         │
   core ◄─────────────────────┘
```

## 2. End-to-End Loops

### The windowed client (`playground_app`, `--scene models` by default)
Start-up order:
1. logging;
2. job system;
3. `Application` (GLFW, window);
4. Vulkan renderer;
5. asset manager;
6. scene.

Shutdown is the reverse, and assets are cleared before the renderer.

Per frame (`engine::Application::run`):
1. **Input:** poll GLFW, snapshot the input, latch the edges.
2. **Simulation:** the fixed-step accumulator decides 0..n steps of 1/120 s.
   Each step runs the scene's `fixedUpdate` (ECS systems). Positions are
   snapshotted first so drawing can blend.
3. **Update** (once per frame): `assets.update()` finishes up to 8 loaded
   assets (GPU uploads happen here, on the main thread); the camera
   controller; key toggles.
4. **Extract:** the scene copies what is visible into `FrameData`: mesh
   instances with materials, sprites interpolated by alpha, the camera,
   the sun, and environment, shadow, bloom and tone-map settings. The
   renderer never reads the ECS.
5. **Render:** `VulkanRenderer::renderFrame`.

Meanwhile, worker threads (`JobSystem`) read and decode files (glTF,
images, HDR panoramas) and hand them to step 3 through one locked queue.

### The rendering pipeline (`render/src/VulkanRenderer.cpp`)
Per frame, two frames in flight:
1. **Wait** on this slot's fence, then **acquire** a swapchain image.
2. **Free** resources destroyed two or more frames ago.
3. **Write** the frame's data into persistently mapped buffers:
   - the mesh draw list (192 B per instance);
   - sprites (opaque first, translucent ones sorted back to front);
   - uniforms (288 B: camera, inverse, light matrix, sun, environment,
     shadow settings).
4. **Record.** When there are meshes or a sky:
   1. **Shadow map:** 2048² `D32_SFLOAT`, depth only, from the sun. The
      box is fitted round a bounding sphere of the scene and snapped to
      texels. Hardware depth bias, negative for reverse-Z.
   2. **HDR scene:** into `R16G16B16A16_SFLOAT` with depth. Meshes are
      drawn one indexed draw each, sharing one buffer of per-draw data
      read by GPU address. Each draw gets:
      - bindless textures (set 1);
      - Cook-Torrance GGX lighting with normal maps;
      - sunlight × shadow visibility (normal offset, 3×3 hardware PCF,
        fade at the map's edges);
      - image-based lighting: irradiance, plus prefiltered specular × the
        BRDF table;
      - emissive.

      Then the sky (its environment cube and the sun's disk) where no mesh
      drew.
   3. **Bloom** (if on): a half-size mip chain. Going down, the first step
      thresholds with a soft knee and uses the Karis average; 13-tap
      filters. Going back up, tent filters added level onto level.
   4. **Swapchain:** the composite (HDR + bloom × strength → exposure →
      ACES or PBR Neutral → sRGB encoded once: by the swapchain if
      `_SRGB`, in the shader if `_UNORM`), then **sprites**, un-tone-mapped,
      depth-tested against the scene.

   Frames with sprites only (the 2D scene) go straight to the swapchain
   step.
5. **Submit, present.** An out-of-date swapchain is rebuilt next frame.
   The HDR target, bloom chain and their descriptor sets are rebuilt with
   it, without leaks.

The environment (a procedural sky by default, or an `.hdr` panorama) is
baked on the GPU when it changes, by four compute shaders: the environment
cube, the irradiance cube, and the GGX-prefiltered specular cube. A fast
procedural sky is baked at start-up, so headless tests stay quick.

### The dedicated server (`playground_app --server [--port N]`)
- It branches off straight after logging starts: no GLFW, no window, no
  Vulkan, no job system. An `InterruptGuard` turns Ctrl+C or SIGTERM into
  a stop request.
- `game::GameServer::start` listens (a few connection slots more than
  players, so a full server can say so) and spawns 64 bouncing balls in an
  ECS. `--net-latency` / `--net-loss` make its outgoing traffic worse.
- Each loop (`app/Server.cpp`):
  1. `pumpNetwork(time until the next tick, at most 8 ms)`: the network
     pump is the loop's sleep. Per event:
     - **connect:** a handshake deadline (3 s) starts;
     - **Hello:** wrong version → `Reject` + `disconnectAfterSending`;
       full → `Reject`; otherwise spawn a player entity (Transform +
       PlayerTag, no Velocity), send `Welcome` (its id, exact spawn) and
       a `Spawn` of everything, and a `Spawn` of the newcomer to the rest;
     - **Input:** into that client's `InputQueue`;
     - **disconnect:** destroy its player, `Despawn` to the rest;
     - then any client past its handshake deadline is disconnected.
  2. The same `FixedStepAccumulator` as the client runs 0..n
     `GameServer::step()`s: each client's queue applies its inputs
     (a token bucket: +1 a tick, at most 3, one per input) with
     `stepPlayer`; balls move and bounce; every 6th tick (20 Hz) each
     client gets its own **Snapshot**: tick, `lastAckedInputSeq`, its exact
     position, then the entities quantized (~6 B each when full). It is a
     **delta** against the newest snapshot the client says it has (each
     Input carries that tick) if the server still holds that one (the
     last 32 sent, per client): gone ids; new entities in full; changed
     ones as offsets in the fewest bits; unchanged ones not at all.
     Otherwise full. Then `flush()`.
  3. A status line every 5 s, with each client's inputs applied, dropped
     (over the rate limit) and lost.
- On stopping: goodbye to every client, waiting up to 500 ms for their
  acknowledgements, then exit 0.

### The network client (`playground_app --connect HOST[:PORT]`)
- The windowed game with `NetScene` instead of a demo scene; the same
  start-up and frame as above. `--headless` swaps the window for a
  scripted bot (`app/Server.cpp`, `runClient`).
- `game::GameClient`: connect → `Hello` → `Welcome` (Playing) or `Reject`
  (Rejected); no welcome within 5 s → Disconnected with the reason.
- Each fixed step (`NetScene::fixedUpdate`): `pumpNetwork(0)`, then
  `step(input)`:
  1. the input is quantized exactly as the server will decode it;
  2. **predicted:** `stepPlayer` applied at once, stored in a 256-entry
     ring `{seq, input, state}`;
  3. sent unreliably with every unacknowledged input up to 8 (redundancy);
  4. the interpolation clock advances a tick.
- Each snapshot: dropped if `tick <= newest seen`. A delta is rebuilt on
  the snapshot it names, from the last 32 the client kept (missing: dropped
  and counted, never seen in tests). The newest tick goes back to the
  server in the next Input. Then it is buffered for interpolation, and
  **reconciled**: the predicted state at
  `lastAckedInputSeq` is compared with the server's exact position; if
  further than 0.01 units, rewind to the server's and replay the later
  inputs. If the ring no longer holds that input (a ping over 2 s), take
  the server's state and replay what is left. The visible jump is spread
  over ~0.25 s (an offset that fades).
- Each frame: the local player is drawn blended between its last two
  predicted ticks (alpha); everything else at the interpolation clock
  (~14 ticks, 117 ms, behind the newest snapshot heard, nudged gently,
  jumping only after a stall), blended between the two snapshots around
  it, holding (not extrapolating) past the newest. Only entities the
  server has spawned for us are drawn.

### How they fit together today
- The client and server share core (clock, fixed step), the ECS and its
  systems, `net/`, and `game/` (the protocol and the movement rule: one
  copy, so prediction matches).
- `netsync_tests` runs a server and two clients in one process over a
  simulated 40 ± 10 ms, 10%-loss network both ways and checks they
  converge exactly.

## 4. Known Limitations & Remaining Roadmap

### Unverified platforms and conditions
- **Windows** has never been built or run: the `windows` preset, MSVC
  warnings, vcpkg's tinygltf, stb, ENet and Jolt packages (with vcpkg's
  Jolt, `find_package(Jolt)` picks it up instead of the vendored copy; its
  build options, e.g. determinism, are vcpkg's, not `cmake/jolt`'s).
- **A real GPU:** everything so far ran on Mesa's CPU driver (llvmpipe)
  under Xvfb. Speeds measured there (release, 1600×900): 3D scene ~83 ms
  a frame, 2D scene ~36 ms.
- **High-DPI displays.**
- **A real network:** only loopback, with latency, jitter and loss
  simulated (`net::NetworkConditions`); never across real machines, Wi-Fi
  or NAT. ENet's own acknowledgements are not delayed by the simulation.
- **The cloud environment's setup script**, until a fresh session runs it.
- `environment_tests` failed once when the virtual display (Xvfb) did not
  start. It hasn't recurred.

### Known limitations (no known bugs)
- **Networking:**
  - snapshots are capped at 128 entities (64 balls + up to 16 players,
    checked at start-up); deltas save little on things that move every
    tick (no velocity-based prediction of positions in the encoding);
  - players only move: no shooting or collision between players yet (the
    Fire button is sent but unused), so nothing needs lag compensation;
  - the movement rule is deterministic within one build; a client built
    with another compiler could disagree by float rounding (it would just
    be corrected);
  - entity ids on the wire are ECS indices (a reused index after a
    despawn is fine because Spawn/Despawn are reliable and ordered, but a
    very late snapshot could briefly show the old entity's position for
    the new one);
  - the input rate limit trims a client's queue past 12 inputs (100 ms):
    after a long freeze a client is corrected rather than allowed to catch
    up all at once;
  - no authentication or encryption; IPv4 only; each `Host` is
    single-threaded; the windowed client shows status in the log, not on
    screen (no HUD text yet).

  Note: ROADMAP §4.11 planned to keep networking inside the game. At the
  user's request we built a generic engine transport (`net/`); game
  messages live in `game/`, not in the engine.
- **Rendering:**
  - one shadow map, no cascades;
  - lamps glow but light nothing (no point lights);
  - no fog, depth of field or HUD text yet (Milestone 4 parity items);
  - no frustum culling or instancing of repeated meshes;
  - one GPU mesh per glTF primitive;
  - `setEnvironment` and every upload wait for the GPU (`submitAndWait`);
  - fences, not timeline semaphores;
  - no Vulkan debug names; no pipeline cache.
- **Physics:**
  - colliders and body settings are read when the body is made (remove
    and re-add a component to change them); shapes do not follow
    `Transform3D.scale`;
  - characters are not bodies: raycasts and dynamic bodies do not hit them
    (they push bodies; bodies do not push them);
  - contact events exist (new contacts only); no triggers, joints or ragdolls yet;
  - physics runs in the 3D demo only: the network game's players still
    move by `game::stepPlayer` (2D, no physics), so there is no
    server-authoritative physics yet.
- **Engine:**
  - only the 3D scene draws from `MeshRenderer` components (an extraction
    in the scene, not yet a shared engine system);
  - glTF without skins, animation, morph targets or alpha modes;
  - the profiler is our own timings, not Tracy; no Vulkan debug names.
- **Audio:**
  - sounds are made from maths or given as PCM: no file loading wired up
    yet (miniaudio's decoders are compiled in, for WAV/FLAC/MP3 later);
  - `AudioSource` is not saved in scene files (clips are runtime ids);
  - no reverb, occlusion or mixer groups; one listener;
  - never heard on this machine (no sound card): device output is
    untested; mixing, 3D and the null device are tested.
- **Cutscenes:**
  - co-op clients play by their estimate of the server tick (as they see
    snapshots), so every player shows the same tick's moment, each about
    their own latency behind the server; movement locking on the client
    can start a round trip before the server's, which shows as a small
    correction hidden by the cutscene;
  - the camera track only (no animated entities or bones yet); event
    actions mean what each scene's handler makes them mean;
  - the 2D network client's handoff blends to an overhead perspective view
    matching its orthographic one, then switches.
- **Developer UI:**
  - the inspector edits components in place; there is no undo, and
    entities cannot be created or have components added from the UI yet;
  - a loaded scene replaces the world's entities but not what the scene
    keeps outside the ECS (the camera; the sky, which stays baked with the
    original sun direction);
  - the network client's profiler shows its numbers; its world (the
    server's) is not editable.
